# 프롬프트 기록

사용자가 전달한 프롬프트(요청) 원문을 시간순으로 기록한다. 새 요청을 받으면 맨 아래에 추가한다.
기능·구현사항으로 정리한 내용은 [SPEC.md](SPEC.md), 변환 규칙은 [CONVERSION_RULES.md](CONVERSION_RULES.md) 에 있다.

## 작업 규칙 (프롬프트로 전달된 상시 지침)

- **문서 관리**: 요청을 기능·세부 구현사항으로 정리해 `docs/SPEC.md` 로, 변환 규칙은 `docs/CONVERSION_RULES.md` 로 관리하고, 결정·요청이 추가될 때마다 갱신한다. (#1-9)
- **자동 커밋**: 작업하면 사용자가 요청하지 않아도 자동으로 커밋한다. (#2)
- **커밋 단위**: 하나의 작업으로 분리할 수 있는 작은 단위로 커밋한다. (예: 서버 API 에 엔드포인트 하나 추가 정도) (#2)
- **커밋 종류 분리**: 문서 수정, 스타일, 리팩토링, 기능 수정, 기능 추가 등 성격이 다른 변경은 서로 다른 커밋으로 분리한다. (#3)
- **브랜치·PR**: 적당한 작업 단위마다 브랜치와 PR 을 만들어 작업한다. 기본 작업 브랜치는 `develop`, 작업 브랜치는 `feature/{번호}-{작업내용}`. (#4)
- **PR 병합 전 확인**: PR 을 병합하기 전에 "머지할까요?" 라고 묻는다. (#14, #11 의 자동 병합을 대체)
- **브랜치 재사용**: 연속된 요청이 같거나 비슷한 부분을 수정하면 새 브랜치를 만들지 않고 기존 브랜치에서 작업한다. (#18)

## #1 (2026-10-10) MVP 요청

> 한국어 자판(쿼티)으로 히라가나를 쓸 수 있는 자판기 앱을 만들어줘. 중요한 것을 제외하고, 자잘한 결정사항은 네 맘대로 해. MVP 버전을 만들어 줘.
>
> 1. 사용자는 시스템 설정에서 이 키보드를 선택할 수 있어야 해.
> 2. 직접 작성해야 하는 로직은 한글 → 히라가나 변환이야. 히라가나 → 가타카나 또는 한자 후보를 보여주는 건 상업적 이용이 가능한 오픈소스를 사용하도록 해. 소스코드 공개 의무는 상관 없어.
> 3. 한글 → 히라가나 매핑은 네가 알아서 만들어줘. 다만 예시는 몇 가지 알려줄게. 만약 일본어에 없는 발음이라면 가장 비슷한 걸로 변환 해.
>     - 가 → が
>     - 각코우, 갓코우 → がっこう
>     - 잣시, 잦시, 잧시 등 → ざっし
> 4. 매핑 시점은 즉각적이지 않아야 해.
>     - 한글이 히라가나로 매핑되는 건 내부 상태일 뿐 사용자가 보는 것은 아니야. 다만 현재의 상태가 자동완성 후보 목록에는 들어가.
>     - 각코우를 입력하면 がっこう가 되어야 해. 만약 한글자씩 즉각적으로 매핑하면 がㄱこう가 되겠지. 이걸 방지하기 위한 로직이야.
> 5. 쉼표, 마침표 등 일본어 자판에 필요한 항목이 있다면 네가 알아서 추가 해. 다만, 참고할 자판으로는 기존의 (삼성) 시스템 키보드의 일본어(쿼티) 자판을 참고하도록 해. 다만 아래 항목은 자판에 넣어줘.
>     - 스페이스 바: 띄어쓰기. 포커싱 중인 글자가 있을 경우 자동완성 이동
>     - 엔터: 현재 포커싱 중인 자동완성을 확인, 포커싱 중인 글자가 없을 경우 검색이나 엔터로 동작
> 6. 글자 입력 / 기호 입력 이렇게 두 가지 모드를 지원해.
> 7. 입력한 문자열은 앱 내에서만 처리하고, 서버로 전송하지 않아.
> 8. 한글 → 히라가나 → 한자 변환 과정의 상태 머신의 설계는 특히 신경 써서 진행해
> 9. 현재 프롬프트로 전달한 내용은 정리해서 md 파일로 관리해. md 파일은 내가 전달한 프롬프트를 기능 및 세부 구현사항으로 정리해야 해. 그리고 변환 규칙도 별도의 md 파일로 생성하여 관리하도록 해. 추가로 결정하거나 전달한 내용도 알아서 추가될 때마다 md 파일을 업데이트 하도록 해.
